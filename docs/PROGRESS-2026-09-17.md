# SnugKV progress — 2026-09-18

> **Historical snapshot:** later on 2026-09-18 the audited ACL milestone, broad
> RESP3 differential sweep, and Streams Redis 8.2 differential edge-case audit
> were completed. Use `PROGRESS.md`, `PLAN.md`, `COMPATIBILITY.md`, and issue #55

This snapshot records the Redis-compatibility state after completing the CLIENT registry/tooling, COMMAND metadata/introspection, and CONFIG compatibility milestones.

## Completed recently

### COPY

The documented single-database `COPY source destination [DB 0] [REPLACE]` surface is complete and live-differentially tested against Redis for return values, tested errors, TTL copying, native datatype preservation, REPLACE behavior, and deep-copy independence. Nonzero destination DBs remain an intentional single-database boundary.

### Read-only scripting and Redis Functions

Completed work includes `EVAL_RO`, `EVALSHA_RO`, Redis Functions core, `FUNCTION DUMP/RESTORE`, Function-library restart persistence, `FUNCTION STATS`, `FUNCTION HELP`, `FUNCTION KILL`, and `SCRIPT KILL`.

Safe Function flags currently supported for SnugKV's single-node semantics are:

- `no-writes`
- `allow-stale`
- `no-cluster`
- `allow-cross-slot-keys`

`SCRIPT DEBUG` remains intentionally deferred until real Redis LDB-style semantics are implemented rather than approximated. `allow-oom` is also deferred until scoped memory-admission semantics can be carried through the function execution context without weakening normal max-memory enforcement.

### CLIENT compatibility

The current CLIENT milestone is complete for the implemented single-node RESP2 scope:

- `CLIENT ID`
- `CLIENT GETNAME`
- `CLIENT SETNAME`
- `CLIENT SETINFO LIB-NAME|LIB-VER`
- `CLIENT INFO`
- `CLIENT LIST`
- `CLIENT LIST ID <id> [<id> ...]`

See `docs/CLIENT-COMPATIBILITY.md` for the detailed CLIENT boundary.

### COMMAND metadata and introspection

Issue #90 is complete for SnugKV's implemented single-node RESP2 surface.

Implemented commands:

- `COMMAND`
- `COMMAND COUNT`
- `COMMAND INFO [command ...]`
- `COMMAND DOCS [command ...]` for the implemented/documented surface
- `COMMAND GETKEYS <command ...>`
- `COMMAND GETKEYSANDFLAGS <command ...>`

The runtime registry currently contains 207 top-level commands after package initialization.

Dynamic key extraction is implemented for EVAL/EVALSHA/EVAL_RO/EVALSHA_RO, FCALL/FCALL_RO, COPY, BITOP, ZSET algebra/store, ZMPOP/BZMPOP, XREAD, and XREADGROUP. The final live Redis 8.2 audit matched the sampled key lists and GETKEYSANDFLAGS classifications.

`COMMAND INFO` returns the Redis 7+/8 ten-field shape and now supports:

- bare `COMMAND INFO` for all registered top-level commands
- direct canonical child lookups such as `CLIENT|ID`
- parent field-10 metadata for `COMMAND`, `CLIENT`, `FUNCTION`, and `SCRIPT`
- supported-child-only advertisement rather than fabricating unsupported Redis subcommands

The final INFO hardening differential matched Redis 8.2 for the original GET/SET/DEL/COPY/EVAL/FCALL/SORT/XADD/PFADD/GEOADD sample and for BITOP, scripting read-only/SHA variants, SORT_RO, ZSET algebra/store/pop, XREAD/XREADGROUP, and implemented parent/child metadata.

`COMMAND DOCS` supports filtering, requested-order preservation, unknown-command omission, recursive arguments, histories, tokens, key-spec indexes, `oneof`/`block` structures, and optional/multiple flags. The final completion pass added the previously missing or abbreviated implemented BITOP, scripting, SORT, ZSET, and Streams documentation plus Redis 8.2 XADD reference-policy option documentation.

The milestone passed focused tests plus the normal race/vet/fuzz/build gates.

See `docs/COMMAND-COMPATIBILITY.md` for the detailed audit record and compatibility boundary.

### CONFIG compatibility

The common Redis CONFIG/tooling surface is now implemented for SnugKV-backed settings:

- `CONFIG GET <pattern> [pattern ...]`
- `CONFIG SET <parameter> <value> [parameter value ...]`
- `CONFIG RESETSTAT`
- `CONFIG REWRITE`
- `CONFIG HELP`

Runtime mutation is real for `maxmemory`, `maxmemory-policy`, `maxclients`, and `appendfsync`. Multi-parameter SET validates the complete request before applying updates. `CONFIG RESETSTAT` resets the server command counter and per-command metrics. `CONFIG REWRITE` atomically persists the effective configuration to the original strict JSON config file when SnugKV was started with `--config`, and returns the Redis-compatible no-config-file error otherwise.

Redis-shaped parent/subcommand metadata and DOCS are implemented for CONFIG, CONFIG|GET, CONFIG|SET, CONFIG|RESETSTAT, CONFIG|REWRITE, and CONFIG|HELP.

Intentional compatibility boundaries remain explicit: SnugKV reports `databases=1`, returns only settings it genuinely implements, and advertises only its real eviction policies. The repository-level `snugkv.json` now captures the normal encoding/compression/JSON-shape runtime profile and `go_memory_limit` (128 MiB) so the common launch path can be `go run ./cmd/snugkv --config ./snugkv.json`.

End-to-end restart validation confirmed rewritten values for maxmemory, maxmemory-policy, maxclients, and appendfsync survive process restart.

## Current roadmap

### Current target: ACL / authentication compatibility

With CONFIG complete for the current single-node RESP2 tooling scope, the next client/tooling milestone is Redis-compatible authentication and ACL behavior.

### Remaining major compatibility areas

- ACL/authentication scope
- RESP3 where required by clients/tooling
- final Streams differential edge audit
- migration/transfer scope beyond DB0 COPY
- exact `allow-oom` Function semantics
- real `SCRIPT DEBUG` / LDB behavior
- optional Redis RDB byte compatibility for Function DUMP/RESTORE

Replication, Sentinel-style failover, and Redis Cluster remain later distributed-scope work rather than blockers for the current single-node target.
