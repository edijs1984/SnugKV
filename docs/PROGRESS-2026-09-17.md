# SnugKV progress — 2026-09-17

This snapshot records the current Redis-compatibility state after completing the CLIENT registry/tooling milestone and substantially implementing the COMMAND metadata milestone.

## Completed recently

### COPY

The documented single-database `COPY source destination [DB 0] [REPLACE]` surface is complete and live-differentially tested against Redis for return values, tested errors, TTL copying, native datatype preservation, REPLACE behavior, and deep-copy independence. Nonzero destination DBs remain an intentional single-database boundary.

### Read-only scripting and Redis Functions

Completed work includes `EVAL_RO`, `EVALSHA_RO`, Redis Functions core, `FUNCTION DUMP/RESTORE`, Function-library restart persistence, `FUNCTION STATS`, `FUNCTION HELP`, `FUNCTION KILL`, and `SCRIPT KILL`.

Safe Function flags currently supported for SnugKV's single-node semantics are:

- `no-writes`
- `allow-stale`
- `no-cluster`
- `allow-cross-slot-keys`

`SCRIPT DEBUG` remains intentionally deferred until real Redis LDB-style semantics are implemented rather than approximated. `allow-oom` is also deferred until scoped memory-admission semantics can be carried through the function execution context without weakening normal max-memory enforcement.

### CLIENT compatibility

The current CLIENT milestone is complete for the implemented single-node RESP2 scope:

- `CLIENT ID`
- `CLIENT GETNAME`
- `CLIENT SETNAME`
- `CLIENT SETINFO LIB-NAME|LIB-VER`
- `CLIENT INFO`
- `CLIENT LIST`
- `CLIENT LIST ID <id> [<id> ...]`
- `CLIENT LIST TYPE NORMAL`
- `CLIENT KILL ID <id> [SKIPME YES|NO]`
- `CLIENT UNBLOCK <id> [TIMEOUT|ERROR]`
- `CLIENT HELP`

The implementation uses a concurrency-safe per-TCP-server client registry and integrates targeted UNBLOCK with existing cancellable blocking command paths so the target socket remains usable after unblocking.

Live Redis 6379 vs SnugKV 6380 testing matched the intended behavior for multiple distinct persistent client IDs, name/library metadata, INFO/LIST reply shape, LIST filtering, targeted KILL, self-kill/SKIPME, UNBLOCK TIMEOUT/ERROR, connection survival, invalid IDs/reasons, and tested arity/error behavior.

See `docs/CLIENT-COMPATIBILITY.md` for the detailed CLIENT boundary.

### COMMAND metadata and introspection

The COMMAND milestone has advanced from basic introspection to a Redis-shaped tooling surface.

Implemented commands:

- `COMMAND`
- `COMMAND COUNT`
- `COMMAND INFO <command ...>`
- `COMMAND DOCS [command ...]` for the implemented/documented subset
- `COMMAND GETKEYS <command ...>`
- `COMMAND GETKEYSANDFLAGS <command ...>`

The runtime command registry currently contains 207 commands after package initialization. Fixed-key extraction reuses the existing `first` / `last` / `step` metadata. Dynamic extraction is implemented for the audited variable-key families including EVAL/EVALSHA/EVAL_RO/EVALSHA_RO, FCALL/FCALL_RO, COPY, BITOP, ZSET algebra/store commands, ZMPOP/BZMPOP, XREAD, and XREADGROUP.

Live Redis differential testing matched the audited key lists and key flags, including Redis's `RO access` classification for XREADGROUP key specs.

`COMMAND INFO` now returns the Redis 7+/8 ten-field shape: name, arity, flags, first/last/step, ACL categories, tips, key specs, and subcommands. The audited sample matched Redis for GET, SET, DEL, COPY, EVAL, FCALL, SORT, XADD, PFADD, and GEOADD, including wire-type details such as bulk-string tips, key-spec notes, dynamic keynum specs, and command-specific key flags.

`COMMAND DOCS` now supports Redis-style requested-name filtering, requested-order preservation, unknown-command omission, recursive argument metadata, history arrays, tokens, key-spec indexes, nested `oneof`/`block` structures, and optional/multiple flags. The audited subset matched Redis for GET, SET, DEL, COPY, EVAL, FCALL, XADD, PFADD, and GEOADD.

The main remaining COMMAND work is parent/subcommand metadata for `COMMAND`, `CLIENT`, `FUNCTION`, and `SCRIPT`, followed by one broader final differential audit before issue #90 is closed.

See `docs/COMMAND-COMPATIBILITY.md` for the detailed boundary and audit record.

## Current roadmap

### Current target: finish COMMAND metadata

Issue #90 remains open only for the final parent/subcommand metadata and broad differential pass. The authoritative metadata/key-extraction path should continue to be reused by future scripting policy, tooling, and ACL work rather than duplicated in independent registries.

### Remaining major compatibility areas

- finish COMMAND parent/subcommand metadata and final audit
- CONFIG compatibility for common tooling
- ACL/authentication scope
- RESP3 where required by clients/tooling
- final Streams differential edge audit
- migration/transfer scope beyond DB0 COPY
- exact `allow-oom` Function semantics
- real `SCRIPT DEBUG` / LDB behavior
- optional Redis RDB byte compatibility for Function DUMP/RESTORE

Replication, Sentinel-style failover, and Redis Cluster remain later distributed-scope work rather than blockers for the current single-node target.
